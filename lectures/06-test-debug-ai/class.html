Lecture 6: Testing, Debugging, and AI-Assisted Programming

Ensuring Code Correctness in Data Analysis

Central Question

How do we know our code actually works – and keeps working as we modify it? How do we use AI tools effectively while maintaining code quality?

In Lecture 5, we wrote functions to clean and analyze data. But how do we know those functions work correctly? What happens when our data has unexpected values? How do we find and fix bugs efficiently? And as AI coding assistants become more powerful, how do we verify that AI-generated code is correct?

Consider a data cleaning function that removes outliers from temperature measurements. If the function has a subtle bug, it might silently corrupt your entire analysis. Your published research could be based on incorrect results. Traditional programming focuses on writing code; professional programming requires verifying code.

Today we’ll learn three essential skills for trustworthy code:

  1. Testing: Writing simple checks that verify functions work correctly
  2. Debugging: Systematically finding and fixing problems when tests fail
  3. AI-Assisted Development: Using LLMs effectively while maintaining quality

By the end of class, you’ll be able to write functions with confidence, knowing they’ll behave correctly even on edge cases. You’ll have strategies for debugging when things go wrong. And you’ll understand how to leverage AI tools productively while avoiding their pitfalls.

These skills are fundamental to reproducible research. Untested code is untrustworthy code.

Assertions and Tests

A test is code that checks whether a function produces the correct output for a given input. The simplest test uses Python’s assert statement:

def test_calculate_mean_normal_case():
    """Test mean calculation with normal data."""
    result = calculate_mean_v1([10, 20, 30])
    expected = 20.0
    assert result == expected, f"Expected {expected}, got {result}"
    print("Test passed: normal case")

test_calculate_mean_normal_case()
Test passed: normal case

The assert statement checks if a condition is true. If false, it raises an AssertionError with the optional message. This makes bugs visible immediately.

Test-Driven Development

A powerful approach is to write tests before writing the function:

  1. Write a test that describes desired behavior
  2. Run the test (it will fail initially)
  3. Write code to make the test pass
  4. Refine the code
  5. Run tests again to ensure nothing broke

This is called test-driven development (TDD). It forces you to think about requirements and edge cases before coding.

def celsius_to_fahrenheit(temps_c):
    """
    Convert list of Celsius temperatures to Fahrenheit.
    
    Args:
        temps_c: list of temperatures in Celsius
        
    Returns:
        list: temperatures in Fahrenheit
    """
    temps_f = []
    for temp in temps_c:
        temp_f = (temp * 9/5) + 32
        temps_f.append(temp_f)
    return temps_f

# Test with known conversions
celsius = [0, 100, -40]
fahrenheit = celsius_to_fahrenheit(celsius)
expected = [32.0, 212.0, -40.0]

# Check each value (floating point requires care)
for i in range(len(expected)):

        f"At index {i}: expected {expected[i]}, got {fahrenheit[i]}"
print("Passed: known conversions")
Passed: known conversions

Testing Floating-Point Values

Floating-point arithmetic is not exact due to binary representation. Instead of:

assert result == 32.0  # Risky!

Use:

assert abs(result - 32.0) < 0.01  # Better!

This checks if values are “close enough” (within tolerance).

Exercise 2.2: Debugging Off-by-One Errors

A common bug in data processing is off-by-one errors – being one position too early or too late:

def get_temperature_range_buggy(temps):
    """Get range of temperatures (max - min)."""
    if len(temps) == 0:
        return None
    
    min_temp = temps[0]
    max_temp = temps[0]
    
    # BUG: This loop doesn't check the last element!
    for i in range(len(temps) - 1):
        if temps[i] < min_temp:
            min_temp = temps[i]
        if temps[i] > max_temp:
            max_temp = temps[i]
    
    return max_temp - min_temp

# Test data where last value matters
temps = [72, 75, 68, 90]  # 90 is the max
result = get_temperature_range_buggy(temps)
print(f"Range: {result}")
print(f"Expected: {90 - 68} = 22")
Range: 7
Expected: 22 = 22

Loop Bounds Debugging

When loops produce wrong results, check:

  1. Does the loop start at the right index?
  2. Does the loop end at the right index?
  3. Are boundary cases handled correctly?

Add debug prints to see what the loop actually processes:

Exercise 2.5: Debugging with the Python Debugger (Optional)

While print debugging is powerful, Python also has a built-in debugger called pdb. You can insert a breakpoint to pause execution and inspect variables:

import pdb

def complex_calculation(data):
    result = 0
    for i, value in enumerate(data):
        pdb.set_trace()  # Execution pauses here
        # You can now type commands like:
        # - 'p value' to print value
        # - 'p i' to print i
        # - 'n' to go to next line
        # - 'c' to continue
        # - 'q' to quit
        result += value * i
    return result

Based on today’s exercises, here are principles for using AI tools effectively:

The AI Assistance Workflow

1. Start with requirements - Write clear specifications before asking AI - Define edge cases and constraints - Know what “correct” means

def calculate_correlation_coefficient(x, y):
    """
    Calculate Pearson correlation coefficient.
    
    This was AI-generated and then verified and refined.
    
    Requirements verified:
    - Handles equal-length lists only
    - Returns value between -1 and 1
    - Returns None for insufficient data (n < 2)
    - Uses sample correlation formula
    
    Args:
        x: list of numeric values
        y: list of numeric values (same length as x)
        
    Returns:
        float: correlation coefficient, or None if insufficient data
    """
    # Validate inputs
    if len(x) != len(y):
        raise ValueError("x and y must have same length")
    
    if len(x) < 2:
        return None
    
    n = len(x)
    
    # Calculate means
    mean_x = sum(x) / n
    mean_y = sum(y) / n
    
    # Calculate correlation
    numerator = sum((x[i] - mean_x) * (y[i] - mean_y) for i in range(n))
    
    sum_sq_x = sum((x[i] - mean_x) ** 2 for i in range(n))
    sum_sq_y = sum((y[i] - mean_y) ** 2 for i in range(n))
    
    denominator = (sum_sq_x * sum_sq_y) ** 0.5
    
    if denominator == 0:
        return None  # One variable has no variance
    
    return numerator / denominator

Synthesis: Building Trustworthy Data Analysis Code

Let’s return to our central questions:

How do we know our code actually works?

  • Write tests that check normal cases and edge cases
  • Use assertions to make requirements explicit
  • Test before you trust

How do we keep code working as we modify it?

  • Re-run tests after every change
  • Add new tests as you discover bugs
  • Document assumptions in tests

How do we use AI tools effectively while maintaining quality?

  • Use AI for generation, but verify everything
  • Write requirements and tests first
  • Treat AI suggestions as drafts, not final code
  • Understand the code before you use it

The workflow for trustworthy code:

  1. Specify: Write clear requirements (what should the function do?)
  2. Test: Write tests that verify requirements (even before coding)
  3. Implement: Write code to meet requirements
  4. Debug: When tests fail, use systematic approaches
  5. Verify: All tests pass and edge cases handled
  6. Document: Explain assumptions and design decisions

Key insights from today:

  • Untested code is untrustworthy code
  • Edge cases are where bugs hide
  • Print debugging is powerful when used systematically
  • AI tools accelerate coding but don’t ensure correctness
  • You are responsible for verifying everything

Testing mindset:

  • Think about what could go wrong
  • Write tests for those scenarios
  • Make tests part of your development process, not an afterthought

Debugging mindset:

  • Bugs are puzzles to solve, not failures
  • Use evidence (print statements, tests) rather than guessing
  • Check your assumptions systematically

AI assistance mindset:

  • AI is a collaborator, not an oracle
  • Verify, don’t trust blindly
  • Understand the code you use

Professional programming is not just about writing code that works once. It’s about writing code you can trust, verify, and maintain over time. These skills distinguish research code that seems to work from research code that produces reliable results.
